## 1. 选题背景：业务背景与选题原因

### 1.1 业务背景：通勤是最高频、最规律、也最容易被做错的出行决策

对大多数城市上班族来说，通勤不是一次性的「导航请求」，而是每周 5 次、每年 250 次左右的重复决策。这个决策真正困难的地方不在路上，而在**出门之前**：

- **时间不可逆**：几点出门必须在看到路况之前决定。等上车打开地图，能做的只剩「换一条同样堵的路」。
- **信息高度割裂**：天气预报在一个 App，实时路况在另一个，限行、地铁故障、临时管制又在别处。用户要在几个界面之间做心算，还算不准。
- **解释严重缺失**：导航说「预计 58 分钟」，但用户不知道这 58 分钟里有多少是常规早高峰、多少是降雨、多少是事故，因此**不知道该不该信**，也不知道「提前 20 分钟到底有没有用」。
- **服务默认被动**：所有地图产品都假设「用户来查」。但通勤是高度规律的重复行为，完全可以在用户开口之前，把结论送到他面前。

以北京为例，一条 20 公里的跨区通勤走廊，平峰可能 35 分钟，早高峰叠加降雨或事故后可能接近 90 分钟。**同样的距离、同样的车，耗时差出 2 倍以上**；而用户唯一的应对方式，往往是「早点出门」或「赌一把」。这两种策略都缺少依据。

### 1.2 现有产品的空白

| 现有能力 | 解决了什么 | 仍然缺什么 |
| --- | --- | --- |
| 实时路况 / 拥堵指数 | 告诉用户「现在堵不堵」 | 不回答「明早几点走」 |
| 路径规划 / ETA | 告诉用户「这条路要多久」 | 不告诉用户「哪条路在明早更稳」 |
| 天气预报 | 告诉用户「明天有雨」 | 不告诉用户「雨会让你多花几分钟」 |
| 地铁 / 公交查询 | 给出替代方案 | 不会在暴雨时主动建议切换 |
| 推送 / 通知 | 可以发消息 | 缺少可解释、可执行的内容，容易变成打扰 |

这些能力拼在一起，已经足够回答「明早怎么走」，但市场上缺少一个把它们**在正确的时间、以正确的粒度**组合起来的产品。

### 1.3 为什么是现在，为什么是高德

1. **数据基础成熟**：高德的天气、交通态势、路径规划 v5（含 TMC 路段级路况）、公交规划、JS API 2.0 已经具备分钟级、路段级的数据基础。
2. **决策可以前置**：通勤走廊固定、时间规律，历史曲线 + 实时校准 + 天气预报足以做出比「拍脑袋」可靠得多的判断。
3. **可解释成为可能**：把总耗时拆成「自由流 / 早高峰 / 天气 / 突发」四段，每一段都能对应到真实接口字段，用户才敢信。
4. **AI 能力可以落地**：高德 MCP / Skill / CLI（amap-gui）让 Agent 能在夜间完成路线预演、地图回放与数据汇总；Web 服务与 JS API 让结论可以直接呈现给用户。

### 1.4 一个具体的早晨

> 周一 07:30，用户打开地图。HappyDriver 已经算好：
> **「今天建议 07:25 出发，比平时早 35 分钟。京通快速四惠段有事故，昌平暴雨，预计 08:53 到，把握 87%。」**
> 用户点「开始导航」，直接出发；不需要搜索终点，不需要在三个 App 之间来回切换。

这就是本作品要交付的体验：**把「看路况」升级为「收结论」，把「上车再查」提前到「出门之前」。**

## 2. 项目介绍：作品目标与架构说明

### 2.1 作品目标

| 层级 | 目标 | 可验证指标 |
| --- | --- | --- |
| 产品目标 | 让用户在出门前 12 小时拿到「出发时间 + 路线」的结论 | 首屏 1 屏内给出结论；3 次点击完成设置 |
| 体验目标 | 预测敢信、能解释、可推翻 | 每条建议附 3 条证据；给出置信度；支持「照旧走」对照 |
| 技术目标 | 真实调用高德开放平台能力，弱网 / 配额受限可降级 | 页面内可见 API 调用日志；断网时用本地快照完整演示 |

### 2.2 用户旅程

```
今晚 21:00   夜间巡航：拉取未来天气 + 走廊实时路况 + 3 条备选路线
              ↓  融合预测，生成未来 7 天的「出发时间表」
明早 07:30   晨间播报：建议提前 ≥10 分钟 → 强提醒（站内卡片 + 系统通知）
              ↓  用户点「看看怎么走」
07:35        地图打开：主路线 + 2 条备选，红黄绿路段高亮，逐段解释
              ↓  点「开始导航」
07:36        唤起高德导航（URI API），行程开始
途中         路况突变（事故 / 暴雨）→ 二次提醒 + 备选路线重排
```

### 2.3 功能说明

1. **7 天出发时间预测**：基于真实天气预报、走廊实时路况、历史早高峰曲线，逐天给出「最晚可行出发时刻」。
2. **可解释决策**：把预计耗时拆成自由流、早高峰、天气、突发四段，用堆叠条呈现；附天气、路况、历史三条证据，可展开原始 API 返回。
3. **恶劣天气与突发路况**：暴雨、事故、地铁故障可注入，推荐时间、风险、置信度与备选路线实时重排，并弹出播报。
4. **主动通知**：站内手机锁屏式通知 + 浏览器系统通知（Notification API）；早上 6–10 点打开页面会自动补一条当日播报。
5. **路线地图**：高德 JS API 2.0 底图、TMC 红黄绿路段、主/备路线、起终点与事故标记，可切换实时路况图层。
6. **一键导航**：通过高德 URI API 唤起导航，完成从「决策」到「出发」的闭环。
7. **可演示性**：控制台支持「时间旅行到明早 07:30」与情景注入，评委无需等待一天即可看到完整闭环。
8. **降级可用**：任一接口失败自动切换到构建期快照，页面功能不缺失。

### 2.4 页面结构

- **晨间播报卡（Hero）**：建议出发时间、与平时的差值、预计到达、风险标签、置信度、三个动作（开始导航 / 换条路 / 时间旅行）。
- **路线地图**：底图、路况图层、主/备路线、起终点与事故标记、路线耗时列表。
- **未来 7 天**：每天一张小卡，显示推荐出发、耗时、天气、风险；点击切换详情。
- **为什么是这个时间**：耗时堆叠条 + 三条证据。
- **备选方案**：驾车备选与地铁方案，标注耗时差与「雨天更稳」。
- **演示控制台**：暴雨 / 事故 / 地铁故障 / 转晴注入，系统通知开关，API 调用日志。
- **设置**：家、公司、平时出发、期望到达、停车/步行缓冲；地址经高德地理编码解析后重算。

### 2.6 预测模型：可解释的轻量融合

对每一天 `d`、每一个候选出发时刻 `t`（常规时间前后 120 分钟，5 分钟粒度）：

```
T_pred(d, t) = T_free × scale × K_time(weekday, t) × K_weather(d) × liveAdj + ΔI(d, t)
```

| 因子 | 含义 | 取值来源 |
| --- | --- | --- |
| `T_free` | 自由流耗时 | 距离 ÷ 城市快速路自由流速度（45 km/h） |
| `scale` | 实时校准 | 当前高德实测耗时 ÷（自由流 × 当前历史系数），把模型拉回真实路况 |
| `K_time` | 走廊历史拥堵曲线 | 按星期 × 10 分钟的早高峰系数表（0.95–2.95），可由真实历史行程回归替换 |
| `K_weather` | 天气影响 | 晴 1.00 / 小雨 1.12 / 中雨 1.22 / 大雨 1.35 / 暴雨 1.50 / 雪 1.45 / 雾 1.30 |
| `liveAdj` | 实时拥堵校准 | 交通态势的 congested + blocked 比例 → 0.94–1.06 |
| `ΔI` | 突发事件 | 事故 +12 分钟起、随时间线性消散；地铁故障 +18 分钟 |

**决策规则**：在候选时刻里，选择「到达时间 ≤ 期望到达时间」概率 ≥ 80% 的**最晚**出发时刻（让用户多睡）；若全部不满足，则给出「最早可行出发 + 预计迟到 X 分钟」的诚实结论。

**风险分**（0–100）：

```
Risk = 0.45 × 时间风险 + 0.30 × 天气风险 + 0.25 × 路况风险
```

**置信度**：D0 92%、D1 86%、D2 79%、D3 72%、D4 60%、D5 56%、D6 52%；天气为外推时再降 6 个百分点。

**可解释**：把 `T_pred − T_free` 拆成「早高峰 / 天气 / 突发」三段，用堆叠条呈现；每条建议都附「天气 / 路况 / 历史」三条证据，点开可看原始 API 字段。

> 说明：高德天气预报接口返回未来 4 天，第 5–7 天由同季节气候先验 + 趋势外推得到，界面标注「趋势外推」，不伪装成实时预报。未来时刻的路况由「历史曲线 × 实时校准」估计，不宣称能预知事故。

### 2.7 数据流与降级

1. **启动**：并行请求家/公司两地天气、走廊 3 个采样点的交通态势、3 条策略的驾车路线、1 条公交路线（共 7 个接口）。
2. **融合**：预测引擎生成 7 天 × 候选时刻矩阵，输出推荐时刻、风险、置信度、耗时拆解。
3. **渲染**：地图绘制主/备路线，时间轴与证据面板联动。
4. **降级**：任一接口失败 → 使用 `assets/js/snapshot.js`（构建期由真实接口生成），顶部显示「快照 + 生成时间」，功能不缺失。
5. **刷新**：手动刷新；夜间巡航由 `scripts/agent-morning.mjs` 定时生成快照与简报。

### 2.8 作品边界

- 预测是估算，不构成出行承诺；界面给出置信度并保留「照旧走」的对照。
- 事故、暴雨、地铁故障为**演示注入**，用于展示系统反应，界面明确标注「演示注入」。
- 家 / 公司地址仅保存在浏览器本地，不上传。

## 3. 商业价值：解决谁的什么问题、价值在哪、如何使用、落地计划

### 3.1 解决谁的什么问题

| 对象 | 具体问题 | HappyDriver 给什么 |
| --- | --- | --- |
| **通勤族（C 端）** | 每天在「几点走」上赌运气；雨天/事故必然迟到；要在多个 App 间心算 | 前一晚给出明天的出发时间与路线；早上 07:30 主动提醒；一键导航 |
| **企业 / 园区（B 端）** | 恶劣天气大面积迟到；班车排班靠经验；错峰缺依据 | 走廊级通勤预测；错峰建议；恶劣天气预案；班车调度参考 |
| **高德平台** | 导航是「出发后」的单次工具流量，缺少「出发前」的高频入口 | 新的决策入口与服务分发位（打车、地铁、充电、咖啡自提）；走廊级通勤画像 |

### 3.2 价值在哪

**用户价值：把不确定性变成可执行的计划。**

- 少迟到：提前识别暴雨、事故，把「必然迟到」变成「早走 20 分钟」。
- 少焦虑：不需要在三个 App 之间做心算，结论 + 原因 + 把握一次给全。
- 多睡：在能赶上的前提下选择**最晚**出发时刻，而不是盲目提前。
- 可量化：按每年 250 次通勤、每次减少 6 分钟无效等待估算，一年约省下 25 小时。

**平台价值：从「工具」变成「习惯」。**

- 提升 DAU / 留存与推送打开率：通勤是天然的每日触点。
- 创造「出发前」的服务分发位：打车、地铁、充电、早餐自提都可以在正确的时间出现。
- 沉淀走廊 × 时段 × 天气的出行画像，反哺路况预测与城市交通治理。

**B 端价值：把「明天大面积迟到」变成可提前干预的运营事件。**

- 企业通勤 SaaS：按园区订阅，提供错峰建议、班车排班、恶劣天气预案。
- 与 HR / 行政系统打通：暴雨日自动推送弹性上班建议。

### 3.3 如何使用

**C 端（3 步）：**

1. 打开页面，授权通知（可选）。
2. 设置家、公司、平时出发时间、期望到达时间，保存后自动重算。
3. 每天晚上看一次「明早建议」，早上收到播报，点「开始导航」出发。

**典型场景：**

- **周一早高峰**：建议 07:50 出发，比平时早 10 分钟，避开京通快速的事故。
- **暴雨预警**：建议 07:35 出发，同时把地铁方案标为「雨天更稳」。
- **临时事故**：注入/检测到事故后，推荐时间继续提前，备选路线重新排序。
- **周末**：自动跳到下个工作日，不打扰。

**B 端（试点）：**

- 园区管理员配置通勤走廊与上班时间，员工扫码订阅。
- 系统在恶劣天气前一日输出「明日迟到风险名单/比例」，供行政决策。

### 3.4 落地计划

| 阶段 | 时间 | 目标 | 关键动作 |
| --- | --- | --- | --- |
| 阶段一：参赛 Demo | 1 个月 | 单城市单走廊跑通闭环 | 真实接口 + 可解释模型 + 在线演示 + 录屏 |
| 阶段二：产品化 | 3 个月 | 进入高德 App 通勤卡片/小组件 | 用户历史行程自动学习 `K_time`；服务端巡航与推送；覆盖 10 条主流走廊 |
| 阶段三：规模化 | 6–12 个月 | 多城市、多模式、B 端版本 | 驾车/公交/骑行组合；企业通勤 SaaS；与天气、交管、地铁运营数据联动 |

**北极星指标**：周活跃通勤用户数 × 建议采纳率。
**过程指标**：播报打开率、导航唤起率、预测误差（MAE）、「提前出门」建议的准确率、B 端续费率。

### 3.5 商业模式

- **C 端免费**：基础预测与播报免费，作为高德 App 的留存功能。
- **C 端增值**：多地址、家庭共享、企业日历同步、历史通勤报告（会员）。
- **B 端订阅**：园区/企业按人数或走廊订阅，提供错峰、班车、恶劣天气预案。
- **平台分发**：在「出发前」场景中分发打车、地铁、充电、早餐等服务，按效果计费。

### 3.6 风险与合规

- **隐私**：家/公司地址属敏感信息，默认本地存储、不上传；服务端仅存脱敏后的走廊 ID。
- **预期管理**：预测带置信度，明确标注「外推」「估算」，不承诺 100% 准确；事故不宣称可预知。
- **合规**：地图与数据均来自高德开放平台，遵守其服务条款；演示 Key 仅用于赛事，正式上线前做域名白名单与配额管理。
