HappyDriver

明早几点走，今晚就知道；路上有变，提前叫你。基于高德天气、交通态势与路径规划，预测未来 7 天的最佳出发时间与路线，把「上车才开地图」变成「出门前就收到结论」。

形态：单页 Web（移动 / 桌面自适应） 走廊：江宁招商名筑 → 中科曙光 数据：高德开放平台实时接口 Demo：可时间旅行

1选题背景：业务背景与选题原因

1.1 业务背景：通勤是最高频、最规律、也最容易被做错的出行决策

对大多数城市上班族来说，通勤不是一次性的「导航请求」，而是每周 5 次、每年 250 次左右的重复决策。真正困难的地方不在路上，而在出门之前：

① 时间不可逆几点出门必须在看到路况之前决定。等上车打开地图，能做的只剩「换一条同样堵的路」。
② 信息高度割裂天气、路况、限行、地铁故障散落在不同 App，用户要在几个界面之间做心算。
③ 解释严重缺失「预计 58 分钟」里有多少是早高峰、多少是降雨、多少是事故？不知道，就不敢信。
④ 服务默认被动所有地图产品都假设「用户来查」，但通勤是高度规律的重复行为，完全可以主动送达。

以北京为例，一条 20 公里的跨区通勤走廊，平峰可能 35 分钟，早高峰叠加降雨或事故后可能接近 90 分钟。同样的距离、同样的车，耗时差出 2 倍以上；而用户唯一的应对方式，往往是「早点出门」或「赌一把」，两种策略都缺少依据。

1.2 现有产品的空白

现有能力解决了什么仍然缺什么
实时路况告诉用户「现在堵不堵」不回答「明早几点走」
路径规划 / ETA告诉用户「这条路要多久」不告诉用户「哪条路在明早更稳」
天气预报告诉用户「明天有雨」不告诉用户「雨会让你多花几分钟」
地铁 / 公交查询给出替代方案不会在暴雨时主动建议切换
推送 / 通知可以发消息缺少可解释、可执行的内容，容易变成打扰

这些能力拼在一起，已经足够回答「明早怎么走」，但市场上缺少一个把它们在正确的时间、以正确的粒度组合起来的产品。

1.3 为什么是现在，为什么是高德

数据基础成熟天气、交通态势、路径规划 v5（TMC 路段级）、公交规划、JS API 2.0 已具备分钟级、路段级数据。
决策可以前置通勤走廊固定、时间规律，历史曲线 + 实时校准 + 天气预报足以做出比「拍脑袋」可靠的判断。
可解释成为可能把总耗时拆成四段，每段都能对应真实接口字段，用户才敢信。
AI 能力可落地高德 MCP / Skill / CLI（amap-gui）让 Agent 在夜间完成路线预演与数据汇总。

1.4 一个具体的早晨

周一 07:30，用户打开地图。HappyDriver 已经算好：
「今天建议 07:30 出发，比平时早 30 分钟。天元中路百家湖段有事故，江宁暴雨，预计 08:53 到，把握 67%。」
用户点「开始导航」，直接出发；不需要搜索终点，不需要在三个 App 之间来回切换。

这就是本作品要交付的体验：把「看路况」升级为「收结论」，把「上车再查」提前到「出门之前」。

2.3 功能说明

7 天出发时间预测基于真实预报、走廊路况、历史曲线，逐天给出最晚可行出发时刻。
可解释决策耗时拆成自由流 / 早高峰 / 天气 / 突发；三条证据可展开原始返回。
恶劣天气与突发暴雨、事故、地铁故障注入后，时间、风险、备选路线实时重排。
主动通知站内锁屏式通知 + 系统通知；早上 6–10 点打开自动补一条。
路线地图JS API 2.0 底图、TMC 红黄绿、主/备路线、事故标记、路况图层。
一键导航高德 URI API，直接唤起导航。
可演示性时间旅行 + 情景注入，评委 30 秒看完完整闭环。
降级可用接口异常自动切换构建期快照，功能不缺失。

2.5 预测模型：可解释的轻量融合

T_pred(d,t) = T_free × scale × K_time(weekday,t) × K_weather(d) × liveAdj + ΔI(d,t)
因子含义来源
T_free自由流耗时距离 ÷ 城市快速路自由流速度（45 km/h）
scale实时校准当前高德实测耗时 ÷（自由流 × 当前历史系数），把模型拉回真实路况
K_time走廊早高峰曲线星期 × 10 分钟系数表（0.95–2.95），可由真实历史行程回归替换
K_weather天气影响晴 1.00 / 小雨 1.12 / 中雨 1.22 / 大雨 1.35 / 暴雨 1.50 / 雪 1.45 / 雾 1.30
liveAdj实时拥堵校准交通态势的 congested + blocked 比例 → 0.94–1.06
ΔI突发事件事故 +12 分钟起、随时间消散；地铁故障 +18 分钟

决策规则：在候选时刻里，选择「到达 ≤ 期望到达」概率 ≥ 80% 的最晚出发时刻（让用户多睡）；若全部不满足，则给出「最早可行出发 + 预计迟到 X 分钟」的诚实结论。

Risk = 0.45 × 时间风险 + 0.30 × 天气风险 + 0.25 × 路况风险   →   0–100 Confidence = 92%(D0) / 86%(D1) / 79%(D2) / 72%(D3) / 60%(D4) / 56%(D5) / 52%(D6)

可解释：把 T_pred − T_free 拆成「早高峰 / 天气 / 突发」三段，用堆叠条呈现；每条建议附「天气 / 路况 / 历史」三条证据，点开可看原始 API 字段。

边界：高德天气预报返回 4 天，第 5–7 天为趋势外推，界面标注「外推」，不伪装成实时预报；未来时刻的路况由「历史曲线 × 实时校准」估算，不宣称能预知事故。

2.6 数据流、降级与边界

7每次刷新并行调用 7 个高德接口
<1.5s首屏数据聚合耗时（实测）
0后端依赖，静态站点即可运行

启动：并行请求两地天气、走廊 3 点交通态势、3 条驾车路线、1 条公交路线 → 预测引擎生成 7 天 × 候选时刻矩阵 → 地图与时间轴联动。

降级：任一接口失败 → 使用 assets/js/snapshot.js（构建期由真实接口生成），顶部显示「快照 + 生成时间」，功能不缺失。

边界：预测是估算，不构成出行承诺；事故、暴雨、地铁故障为演示注入并明确标注；家 / 公司地址仅保存在浏览器本地。

3商业价值：解决谁的什么问题、价值在哪、如何使用、落地计划

3.1 解决谁的什么问题

对象具体问题HappyDriver 给什么
通勤族（C 端）每天在「几点走」上赌运气；雨天/事故必然迟到；多 App 心算前一晚给出明天的出发时间与路线；07:30 主动提醒；一键导航
企业 / 园区（B 端）恶劣天气大面积迟到；班车排班靠经验；错峰缺依据走廊级通勤预测；错峰建议；恶劣天气预案；班车调度参考
高德平台导航是「出发后」的单次工具流量，缺少「出发前」的高频入口新的决策入口与服务分发位；走廊级通勤画像

3.2 价值在哪

少迟到提前识别暴雨、事故，把「必然迟到」变成「早走 20 分钟」。
少焦虑结论 + 原因 + 把握一次给全，不用在三个 App 之间做心算。
多睡在能赶上的前提下选择最晚出发时刻，而不是盲目提前。
可量化按每年 250 次通勤、每次省 6 分钟估算，一年约省 25 小时。

平台价值：提升 DAU / 留存与推送打开率；创造「出发前」的服务分发位（打车、地铁、充电、早餐自提）；沉淀走廊 × 时段 × 天气的出行画像，反哺路况预测与城市交通治理。

B 端价值：把「明天大面积迟到」变成可提前干预的运营事件；企业通勤 SaaS 按园区订阅，提供错峰、班车、恶劣天气预案。

3.3 如何使用

第 1 步
打开页面

首屏直接看到下一次通勤的结论；授权通知可选。

第 2 步
设置通勤

家、公司、平时出发、期望到达、停车/步行缓冲；地址经高德地理编码解析后自动重算。还可把「明天」指定成周一至周日任意一天，7 天预测与周末系数随之平移，方便演示和复盘特定日期。

第 3 步
每天使用

晚上看「明早建议」，早上收到播报，点「开始导航」出发。

周一早高峰：07:50 出发，避开事故 暴雨预警：07:35 出发，地铁更稳 突发事故：07:25 出发，备选重排 周末：自动跳到下个工作日

3.5 商业模式

C 端免费基础预测与播报免费，作为高德 App 的留存功能。
C 端增值多地址、家庭共享、企业日历同步、历史通勤报告（会员）。
B 端订阅园区 / 企业按人数或走廊订阅，提供错峰、班车、天气预案。
平台分发在「出发前」场景分发打车、地铁、充电、早餐，按效果计费。

3.6 风险与合规

  • 隐私：家 / 公司地址默认本地存储、不上传；服务端仅存脱敏走廊 ID。
  • 预期管理：预测带置信度，明确标注「外推」「估算」；不承诺 100% 准确，不宣称可预知事故。
  • 合规：地图与数据均来自高德开放平台，遵守服务条款；演示 Key 仅用于赛事，正式上线做域名白名单与配额管理。
