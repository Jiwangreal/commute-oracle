## 1. 选题背景

### 1.1 一个每天都在发生的小型决策灾难

北京早高峰，回龙观到上地 15 公里的路，同一辆车、同一个时间，周一要 42 分钟，周三下雨要 68 分钟，遇到京藏高速事故可能要 95 分钟。绝大多数人的应对方式是：**上车、点火、打开地图、看到一片红、然后焦虑**。

问题不在于地图不够好，而在于**决策发生得太晚**：

1. **时间上的滞后**：路况是出发后才看到的，而「几点出门」这件事必须在出发前决定。等看到拥堵，能做的只剩「换一条同样堵的路」。
2. **信息上的割裂**：天气预报在一个 App、路况在另一个、限行/地铁故障又在别处。用户要在三个 App 之间做心算，还算不准。
3. **解释上的缺失**：导航说「预计 58 分钟」，但用户不知道这 58 分钟里有多少是天气、多少是事故、多少是常规早高峰，因此**不知道该不该信**，也不知道「提前 20 分钟到底有没有用」。
4. **主动性上的空白**：所有地图产品默认「用户来查」。但通勤是高度规律的重复行为，完全可以在用户开口之前就把答案送到。

### 1.2 我们想做的事

把「上班路上查地图」提前到**前一晚 21:00 和当天早上 07:30**，把「看路况」升级为「收结论」：

> 「明早建议 **08:05** 出门，比平时早 25 分钟。京藏高速西三旗段 07:50–08:40 拥堵概率 82%，昌平有中雨，骑行和步行接驳不建议。预计 09:26 到公司，把握 86%。」

用户不需要理解模型，只需要知道**几点走、为什么、有多确定**，以及一个「开始导航」按钮。

### 1.3 为什么是现在

- 高德的天气、交通态势、路径规划、路况图层已经具备**分钟级、路段级**的数据基础；
- 大模型与规则引擎的结合，让「多源信息的可解释融合」成本大幅下降；
- 通勤是最高频、最规律、最容易做准的场景——**先做窄，再做深**。

## 2. 项目介绍

### 2.1 目标

| 层级 | 目标 | 可验证指标 |
| --- | --- | --- |
| 产品目标 | 让用户在出门前 12 小时就拿到「出发时间 + 路线」的结论 | 首屏 1 屏内给出结论；3 次点击内完成设置 |
| 体验目标 | 预测要敢信、能解释、可推翻 | 每条建议附 3 条证据；给出置信度；支持「我偏要按原时间走」的对照 |
| 技术目标 | 真实调用高德开放平台能力，弱网/额度受限可降级 | 页面内可见 API 调用日志；断网时用本地快照仍可完整演示 |

### 2.2 用户旅程

```
今晚 21:00   巡航任务启动：拉取未来天气 + 走廊实时路况 + 3 条备选路线
              ↓  融合预测，生成未来 7 天的「出发时间表」
明早 07:30   晨间播报：如果建议提前 ≥10 分钟 → 强提醒（站内卡片 + 系统通知）
              ↓  用户点「看看怎么走」
07:35        地图打开：主路线 + 2 条备选，红黄绿路段高亮，逐段解释
              ↓  点「开始导航」
07:36        唤起高德导航（URI API），行程开始
途中         路况突变（事故/暴雨）→ 二次提醒 + 备选路线重排
```

### 2.3 产品形态与页面结构

单页应用，一屏完成核心闭环：

1. **晨间播报卡（Hero）**：建议出发时间、与平时的差值、预计到达、风险标签、置信度、三个动作（开始导航 / 换条路 / 今天照旧）。
2. **路线地图**：高德 JS API 2.0 底图 + 实时路况图层 + 主路线/备选路线绘制 + 起终点与途经点标记。
3. **未来 7 天时间轴**：每天一张小卡，显示推荐出发时间、预计耗时、天气、风险等级；点击切换地图与解释。
4. **为什么（证据面板）**：把总耗时拆成「自由流 / 早高峰 / 天气 / 突发事件」四段，用堆叠条展示每一段的增量。
5. **演示控制台（Demo Console）**：「时间旅行到明早 07:30」「注入暴雨」「注入事故」「模拟地铁故障」「注入后立即重算」——让评委在 30 秒内看到系统的反应，而不用等一天。
6. **API 调用日志**：每条真实请求的接口、耗时、返回摘要，证明「不是手写死数据」。

**关键设计**：产品页不依赖后端。所有能力都通过浏览器直连高德开放平台（JS API 走 `<script>`，REST 走 CORS），因此可以零成本部署到 GitHub Pages，评委点开即用。后续接入服务端时，只需把 `data.js` 的 fetch 换成自有 API，预测引擎与 UI 不动。

### 2.5 预测模型（可解释的轻量融合）

对每一天 `d`、每一个候选出发时刻 `t`（常规时间前后 90 分钟，5 分钟粒度）：

```
T_pred(d, t) = T_free × K_time(d, t) × K_live × K_weather(d) + ΔI(d, t)
```

| 因子 | 含义 | 取值来源 |
| --- | --- | --- |
| `T_free` | 自由流耗时 | 高德路径规划返回的 duration ÷ 当前拥堵系数 |
| `K_time` | 走廊历史拥堵曲线 | 按星期 × 10 分钟的早高峰系数表（0.95–1.9），可由真实历史行程回归替换 |
| `K_live` | 实时路况校准 | 交通态势返回的 congested / blocked / expedite 比例 → 0.90–1.25 |
| `K_weather` | 天气影响 | 晴 1.00 / 多云 1.02 / 小雨 1.12 / 中雨 1.22 / 大雨 1.35 / 暴雨 1.50 / 雪 1.45 / 雾 1.30 |
| `ΔI` | 突发事件 | 事故 +8~15 min、地铁故障换乘 +20 min，随消散时间半衰 |

**决策规则**：在候选时刻里，选择「到达时间 ≤ 期望到达时间」概率 ≥ 80% 的**最晚**出发时刻（让用户多睡），若全部不满足，则给出「最早可行出发 + 预计迟到 X 分钟」的诚实结论。

**风险分**（0–100）：

```
Risk = 0.45 × 时间风险 + 0.30 × 天气风险 + 0.25 × 路况风险
```

**置信度**：D0 92%、D1 85%、D2–D3 70%（真实预报覆盖）、D4–D6 50%（趋势外推，UI 明确标注「外推」）。

**可解释**：把 `T_pred − T_free` 拆成四段，用堆叠条呈现；每条建议都附「天气 / 路况 / 历史」三条证据，点开可看原始 API 字段。

> 说明：高德的天气预报接口返回 4 天，第 5–7 天由同季节气候先验 + 趋势外推得到，界面标注为「外推」，不伪装成实时预报。路况的「未来时刻」由历史曲线 × 实时校准估计，不宣称能预知事故。

### 2.6 数据流与降级

1. **启动**：并行请求天气（家/公司两个 adcode）、走廊 3 个采样点的交通态势、3 条策略的驾车路线、1 条公交路线。
2. **融合**：`predict.js` 生成 7 天 × 候选时刻矩阵，输出推荐时刻、风险、证据。
3. **渲染**：地图绘制主/备路线，时间轴与证据面板联动。
4. **降级**：任一接口失败 → 使用 `data/fallback-snapshot.json`（构建时由真实接口生成），页面顶部显示「快照模式 + 生成时间」，功能不缺失。
5. **刷新**：手动「刷新实时数据」；夜间巡航由 `scripts/morning-brief.mjs` 定时生成快照。

### 2.7 高德 AI 能力的使用

- **amap-gui（CLI / Skill）**：Agent 侧的「手和眼」。夜间巡航用 `amap-gui route` 预演路线、用 `mapState` 回放视角、用 `searchPOI` 校准起终点；产物写入快照，供页面消费。
- **JS API 2.0**：用户侧的地图与交互。底图、实时路况图层、路线绘制、起终点标记、点击联动。
- **Web 服务 API**：事实来源。地理编码、天气、交通态势、路径规划。
- **URI API**：闭环的最后一公里，一键唤起高德导航。

## 3. 商业价值

### 3.1 解决谁的问题

- **通勤族（C 端）**：少迟到、少焦虑、多睡 10 分钟。按一线城市 1 小时通勤、每周 5 天计算，一年 250 次通勤，哪怕每次只减少 6 分钟无效等待，也是 25 小时。
- **企业/园区（B 端）**：错峰上班、班车调度、恶劣天气预案。把「明天大面积迟到」变成可提前干预的运营事件。
- **平台（高德）**：把「出发后导航」的单次工具型流量，变成「出发前决策」的高频服务入口。

### 3.2 价值在哪

| 维度 | 价值 |
| --- | --- |
| 用户价值 | 决策前置：从「看到红再焦虑」变成「昨晚就知道」。可解释：知道为什么，才敢信。可选择：给备选而不是命令 |
| 平台价值 | 提升 DAU/留存与推送打开率；创造「出行前」的新广告/服务分发位（打车、地铁、充电、咖啡自提）；沉淀走廊级通勤画像 |
| 数据价值 | 走廊 × 时段 × 天气的出行画像，可反哺路况预测与城市交通治理 |
| B 端价值 | 企业通勤 SaaS：按园区订阅，提供错峰建议、班车排班、恶劣天气预案 |

### 3.3 如何落地

**阶段一（本次参赛，1 个月）**：单城市单走廊的 Web Demo；真实数据 + 可解释模型；完成在线演示与录屏。
**阶段二（3 个月）**：接入高德 App 通勤卡片/小组件；用户历史行程自动学习 `K_time`；服务端巡航与推送；覆盖 10 条主流走廊。
**阶段三（6–12 个月）**：多城市、多模式（驾车/公交/骑行/步行组合）；企业版；与天气、交管、地铁运营数据联动。

**北极星指标**：周活跃通勤用户数 × 建议采纳率。
**过程指标**：播报打开率、导航唤起率、预测误差（MAE）、「提前出门」建议的准确率。

### 3.4 风险与边界

- **隐私**：家/公司地址属敏感信息，默认本地存储、不上传；服务端仅存脱敏后的走廊 ID。
- **预期管理**：预测有置信度，明确标注「外推」「估算」，不承诺 100% 准确；异常事件（事故）不宣称可预知，只做「发生后的快速响应」。
- **合规**：地图与数据均来自高德开放平台，遵守其服务条款；演示 Key 仅用于赛事演示，正式上线前做域名白名单与配额管理。

## 6. 附录：3 分钟演示剧本

1. **00:00–00:20** 打开页面：先看到「明早 08:05 出发，比平时早 25 分钟」，右上角 LIVE 与数据时间。
2. **00:20–00:50** 点「为什么」：总耗时拆成自由流 24 min / 早高峰 +12 min / 天气 +9 min / 事故 +8 min，三条证据卡片。
3. **00:50–01:20** 切到「未来 7 天」：周三大雨风险 78，建议 07:40 出发；周五四天预报外推，标注「外推」。
4. **01:20–02:00** 打开演示控制台：注入「明早暴雨」→ 推荐时间从 08:05 跳到 07:35，Hero 变红，系统通知弹出（真实 Notification API）。
5. **02:00–02:30** 注入「京藏高速事故」→ 地图出现事故标记，主路线耗时重算，备选路线重新排序。
6. **02:30–03:00** 点「开始导航」→ 唤起高德 URI，展示 API 日志：天气、交通态势、路径规划、JS API 全部真实调用。
